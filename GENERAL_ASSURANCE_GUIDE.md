# General Assurance Kernel 4.3

Minimal engagement begins before lifecycle execution. `clses-intake` reads existing context and the composed profile, asks only irreducible material questions, and emits a consolidated baseline proposal for explicit human review. It has no authority effect.

`clses-operator` presents that engagement and subsequent execution as one six-step journey. Its plain-language view and consolidated review packets are projections of governed state, not alternate authority or evidence stores.

The `software-quality` profile adds reusable quality dimensions and measurable criteria to the same lifecycle graph. System-class overlays inherit those controls and add their own. Context tags select optional criteria, named authorities establish thresholds, evidence adapters measure them, and change kinds identify affected conclusions for reassessment.

CLSES 3.0 separates universal assurance invariants from system-specific lifecycle obligations.

## Architecture

The assurance kernel knows only the invariant semantics of identity, ownership, trace relationships, evidence provenance, authority, freshness, deployed state, outcome realization, continuing justification, change impact, and closure. It does not assume a programming language, agent, repository, CI service, cloud, scanner, monitoring platform, or regulatory regime.

Lifecycle profiles declare the domains, required relationships, controls, evidence types, authority roles, and maximum evidence ages that apply to a system class. `base-production` covers intent, outcome realization, governance, requirements, architecture, implementation, verification, security and privacy, supply chain, release, deployment, operations, incident response, resilience, change, and retirement. Overlays add obligations without weakening their parent. Included overlays cover point-of-sale and SaaS systems.

Adapters execute outside the authority kernel. Each immutable adapter manifest declares capabilities, trust anchor, process boundary, command, and timeout. Requests and results use exact versioned envelopes. Results are accepted only when the request, adapter identity and digest, evidence type, timestamps, measurements, and deadline agree. An adapter can measure; it cannot approve its own evidence.

## Lifecycle use

1. A human authority establishes purpose, system class, operating conditions, risk posture, and applicable profiles.
2. The kernel composes the base profile and overlays, rejecting cycles and duplicate controls.
3. Humans and agents create owned lifecycle records and required trace relationships.
4. Bounded execution agents implement changes through the existing mandate and signed-record control plane.
5. Evidence adapters evaluate every control against the exact artifact and environment.
6. The role named by each control makes a separate, evidence-bound decision. Execution agents are never authority actors.
7. The exact release is deployed, and its current byte inventory is reconciled with the authorized artifact.
8. Governance closes the assessment only when every control decision, lifecycle domain, required relationship, change reassessment, and evidence horizon is complete.
9. Any material change or evidence expiry makes affected conclusions non-current and requires fresh evidence and decisions.
10. Retirement remains governed even after normal operations end.

## Verdict meaning

`purpose_achieved_and_sustained_for_declared_profile_and_current_conditions` is deliberately narrow. It applies only to the named system, beneficiaries, hypotheses, composed profile, operating conditions, current environment and deployed inventory, adapter identities, external trust anchor, evidence interval, and continuation review date. It is not transferable to another deployment and is not a universal or permanent certification.

The release package demonstrates the kernel with a controlled point-of-sale dossier. A real production system must replace every demonstration adapter and evidence item with authentic target-environment integrations.
